# gup `0.3.0`

> **TL;DR** — `gup` devient réellement multiplateforme. macOS passe du statut « ça compile » à cible de premier rang : Homebrew (formulae + casks), Mac App Store et MacPorts sont des providers à part entière, et un binaire installé par brew est enfin reconnu comme tel au lieu d'être classé `manual` et masqué du scan. Côté Linux, l'appartenance d'un binaire se résout via `dpkg -S` / `rpm -qf`. **Breaking : Node ≥ 22.13 requis** (auparavant ≥ 20).

`npm i -g @charles_lindecker/gup@0.3.0`

---

## ⚠️ Breaking

### Node ≥ 22.13.0

`engines` passe de `>=20` à `>=22.13.0`, et la cible tsup de `node20` à `node22`.

Node 20 est EOL depuis le 2026-04-30. Continuer à l'annoncer revenait à revendiquer le support d'un runtime qui ne reçoit plus de correctifs de sécurité — pour un outil dont le métier est justement de maintenir une machine à jour, la contradiction était difficile à tenir. Les deux lignes encore supportées sont testées en CI : **22** (Maintenance LTS, jusqu'au 2027-04) et **24** (Active LTS, jusqu'au 2028-04).

La cible de build suit `engines` désormais : compiler pour un runtime plus ancien down-level silencieusement de la syntaxe que les runtimes réellement supportés exécutent nativement, et laisse passer sans broncher du code qui exige un runtime plus récent.

```bash
node --version   # doit être >= 22.13.0
```

## ✨ macOS, pour de vrai

### 🍺 4 nouveaux providers OS (130 → 134)

| Provider | id | Couvre |
|---|---|---|
| Homebrew (formulae) | `brew` | Le gros du CLI sur un Mac. **Pas restreint à darwin** : Linuxbrew (`/home/linuxbrew/.linuxbrew`) passe par le même provider. |
| Homebrew (casks) | `brew-cask` | Applications GUI et distributions binaires posées dans `/Applications` (Docker Desktop, VS Code, IDE JetBrains, navigateurs…). |
| Mac App Store | `mas` | La part d'un Mac qu'aucun autre provider n'atteint : installs sandboxées dont la mise à jour est derrière l'auth du Store. |
| MacPorts | `macports` | L'autre arbre de ports macOS. Coexiste avec Homebrew sur la même machine et reste invisible pour tout le reste. |

Trois décisions volontaires, parce qu'elles changent le comportement observable :

- **`brew` et `brew-cask` sont séparés**, pas un seul provider à deux modes. La commande d'upgrade diffère (`brew upgrade --formula` vs `--cask`) et les casks sont la moitié bruyante : `gup list --only brew` exprime maintenant « les formulae seulement ».
- **`--greedy` est délibérément omis** sur les casks. Sans lui, brew masque les casks marqués `auto_updates true` (Chrome, Firefox, VS Code…). Ces apps se mettent à jour toutes seules au lancement ; forcer l'upgrade re-télécharge un bundle applicatif complet pour atteindre une version que l'app serait allée chercher de toute façon.
- **`HOMEBREW_NO_AUTO_UPDATE=1` n'est pas forcé.** Un scan contre un index périmé rapporterait « rien à mettre à jour » — exactement le mode de défaillance que ce provider existe pour supprimer. Qui veut un scan strictement hors-ligne exporte déjà la variable ; on en hérite.

`brew` refuse explicitement de tourner sur win32. Ce n'est pas cosmétique : certains posent un shim `brew.cmd` sur le PATH Windows pour rebondir dans WSL (ce pont, c'est le provider `wsl-brew`), et sans ce garde-fou gup lancerait `brew outdated` / `brew upgrade` côté Windows.

### 🔎 Détection de la source d'installation : brew, apt, dnf

C'est le correctif qui débloque tout le reste. `InstallSource` gagne `brew`, `apt` et `dnf`, et deux raffinements POSIX se greffent sur le simple match de chemin :

**Résolution des symlinks.** Homebrew installe dans un préfixe privé et n'expose qu'un lien sur le PATH :

```
/opt/homebrew/bin/kubectl → ../Cellar/kubernetes-cli/1.36.3/bin/kubectl
```

`which` rapporte le lien. Sans `realpath`, **tout install brew était classé `manual` — et les entrées `manual` sont écartées des résultats de scan.** Autrement dit : des upgrades bien réelles étaient silencieusement masquées sur macOS. C'est corrigé, et `core/ownership.ts` partage la même résolution pour que les deux détecteurs classent un shim Homebrew par sa vraie localisation Cellar.

**Sonde base de paquets.** Les paquets distro atterrissent dans des préfixes partagés (`/usr/bin`) qui ne portent aucun signal d'appartenance dans le chemin ; `dpkg -S` / `rpm -qf` sont la seule réponse fiable.

La classification Homebrew est volontairement conservatrice : un segment `Cellar` ne compte **que** sous un préfixe connu (`/opt/homebrew`, `/usr/local`, `/home/linuxbrew/.linuxbrew`, `~/.linuxbrew`). Matcher `cellar` seul routerait `brew upgrade` vers un binaire que brew ne possède pas si un utilisateur a un dossier nommé `cellar` — c'est précisément la mauvaise classification que `tests/security/install-source.test.ts` verrouille. `/usr/local` est le seul préfixe non-exclusif à brew (c'est aussi l'emplacement classique d'une install manuelle), donc il n'est accepté qu'en combinaison avec un segment Cellar/Caskroom, jamais seul.

La branche win32 est inchangée : pas d'appel realpath, pas de sonde.

### 🧩 JetBrains et Eclipse détectés sur macOS

Les IDE JetBrains sont maintenant cherchés dans `/Applications`, `~/Applications` et l'arbre Toolbox sous `Application Support`. Un `.app` posé par `brew install --cask` est suivi jusqu'au Caskroom. Le scan des bundles est élagué (`Contents/Resources` n'est pas ré-exploré) pour ne pas transformer un balayage de `/Applications` en parcours récursif complet. Eclipse suit le même traitement.

Passage groupé sur les autres providers IDE (Cursor, VSCodium, Windsurf, Zed, Sublime, Obsidian, Notepad++, Unity Hub) pour que leurs chemins soient dérivés de la plateforme au lieu d'être supposés Windows.

### 💬 Hints d'installation par plateforme

`gup doctor` affiche l'`installHint` d'un provider absent. Un `winget install …` codé en dur est activement inutile sur un Mac. Les providers déclarent désormais un hint par plateforme via `pickInstallHint({ win32, darwin, linux, fallback })`, résolu à la construction du registre. `fallback` est obligatoire : un hint n'est jamais vide, y compris sur une plateforme que personne n'a énumérée.

Au passage, les ids Homebrew sont mappés pour les providers concernés (`brew install kubernetes-cli` plutôt qu'une URL générique).

## 🐛 Fixes

### `gup --version` ne ment plus

La version était redéclarée **deux fois** dans les sources — `src/cli.ts` et l'en-tête du menu — et les deux copies avaient dérivé à `0.1.0` alors que le paquet était publié en `0.2.2`. `gup --version` mentait, et donc chaque rapport de bug qui la citait aussi.

`src/core/version.ts` lit maintenant `package.json`, avec deux emplacements candidats (le graphe de modules est plat après bundling tsup, imbriqué en dev) et une validation par `name` pour qu'un `package.json` parent égaré ne puisse pas être ramassé. Ne lève jamais : un `package.json` introuvable renvoie `0.0.0` plutôt que d'empêcher le CLI de tourner.

### UTF-8 doublement encodé dans les parsers bun et winget

Des sources contenaient du mojibake — de l'UTF-8 relu en latin-1 puis ré-encodé. Ce n'était pas cosmétique, c'était dans les **regex** :

| Fichier | Motif cassé | Conséquence |
|---|---|---|
| `providers/node/bun-global.ts` | `â”œâ”€â”€` au lieu de `├──` | L'arborescence de `bun pm ls -g` ne matchait pas → **zéro paquet bun global détecté**. |
| `providers/os/winget.ts` | `mises\s+Ã ` au lieu de `mises\s+à` | La ligne de fin de tableau n'était pas reconnue sur un Windows en français → parsing du tableau winget faussé. |

### Le runner refusait les chemins courts Windows 8.3

`SAFE_COMMAND_PATTERN`, l'allowlist qui filtre le nom de commande avant tout spawn, n'incluait pas `~`. Or Windows renvoie une forme 8.3 pour tout répertoire dont le nom dépasse 8 caractères ou contient un espace : `C:\PROGRA~1\nodejs\npm.cmd`, `C:\Users\CHARLE~1\scoop\shims\gh.exe` sont des entrées de PATH ordinaires, et `%TEMP%` lui-même est en forme courte dès que le nom d'utilisateur dépasse 8 caractères.

Sur ces machines, gup refusait de lancer un binaire parfaitement légitime avec `runner: refusing to spawn unsafe command name`. `~` est ajouté à l'allowlist et couvert par des cas de test explicites.

Le caractère reste inerte vis-à-vis de l'injection : tout callsite qui dérive un nom de commande depuis un chemin passe par execa sans interprétation shell, où argv est transmis comme vecteur ; l'unique callsite routé par un shell (scoop) passe un littéral fixe, jamais un chemin dérivé.

### `manualChunks` cassait le build de la landing

Le bump Dependabot **vite 6.4.2 → 8.0.16** (PR #46) a remplacé Rollup par **Rolldown**, qui n'accepte que la forme fonction de `manualChunks` — la map objet abortait le build avec `TypeError: manualChunks is not a function`. Le workflow `pages` échouait donc à chaque push touchant `index/` depuis le 2026-08-06, et la landing n'était plus redéployée.

Config passée en forme fonction (comprise par les deux bundlers). `scheduler` rejoint volontairement le chunk `react` : c'est une dépendance runtime de react-dom, et l'omettre l'échoue dans le chunk d'entrée, ce qui annule l'intérêt du split.

## 🧪 Tests & CI

### Le premier test qui spawne réellement un process

Toutes les autres suites mockent `execa` en bloc (`tests/core/runner.test.ts` fait `vi.mock("execa")`), ce qui veut dire que **la suite entière pouvait être verte avec la couche de spawn cassée**. Cet angle mort est devenu porteur au moment du passage execa 9 → 10 : execa a abandonné cross-spawn pour son propre résolveur de PATH et son propre échappement cmd.exe, donc *toutes* les commandes que gup lance sous Windows sont construites différemment — et rien ne l'exerçait.

`tests/integration/runner-spawn.test.ts` ajoute 15 tests délibérément non-mockés et délibérément peu coûteux, pour qu'ils tournent sur les six legs de CI : round-trip argv avec métacaractères, non-expansion des variables des deux shells, argument vide préservé, décodage UTF-8, exit non-zéro sans throw, binaire absent, séparation stdout/stderr, résolution de PATH — plus les cas Windows sur les shims `.cmd` (npm, pnpm, yarn, corepack, gcloud, az…), qui sont exactement le chemin de code qui a changé.

C'est ce fichier qui a fait remonter le bug `~` ci-dessus : le runner GitHub a un `%TEMP%` en forme courte (`C:\Users\RUNNER~1\…`).

### Matrice CI étendue

`gup` délègue à un gestionnaire de paquets différent sur chaque plateforme et construit des chemins spécifiques à l'OS — une matrice mono-OS ne peut structurellement pas attraper une régression sur les deux autres.

| Avant | Après |
|---|---|
| `windows-latest` × Node 20, 22 | `windows-latest`, `macos-latest`, `ubuntu-latest` × Node **22, 24** |

Windows reste la cible primaire ; macOS et Linux deviennent de premier rang depuis la délégation Homebrew/apt/dnf.

**Ajout du gate lint.** `CONTRIBUTING` listait le lint dans les prérequis de PR, mais aucun workflow ne le lançait — un bump d'eslint pouvait introduire des violations que rien ne remontait. Restreint à un seul leg (`ubuntu-latest` / Node 24) : la sortie eslint ne varie ni par OS ni par ligne Node, la lancer six fois ne ferait que ralentir la matrice.

## 🤖 Dependabot reconfiguré

`.github/dependabot.yml` passe en posture *security-first*. Le raisonnement complet est dans les commentaires du fichier ; en résumé :

| | Avant | Après |
|---|---|---|
| Cadence | hebdomadaire | **mensuelle** |
| Fenêtre de décantation | aucune | **`cooldown`** — 7 j (patch) / 14 j (minor) / 30 j (major) |
| Couverture | `/` npm + `/` actions | **+ `/index`** (la landing ne bougeait que sur CVE) |
| Correctifs de sécurité | dispersés | **groupés**, et non soumis au cooldown ni à la limite de PR |
| Label `security` | posé sur tout, sans effet | retiré (c'était une string, pas un filtre) |

Le point clé : `cooldown` ne s'applique **qu'aux version updates**. Un correctif d'advisory arrive le jour de sa publication, quoi que dise le planning. Ce sont les bumps de routine qui attendent que l'écosystème ait eu le temps de regarder — la plupart des compromissions npm (event-stream, ua-parser-js, node-ipc, chalk/debug) ont été détectées et dépubliées en quelques heures à quelques jours.

Un seul `ignore` est posé, sur les majeures de `@types/node`, parce que `ignore` est la seule option qui bâillonne *aussi* les security updates — et qu'un paquet de types ne transporte pas de code exécutable. Les autres majeures ne sont pas ignorées, seulement ralenties par le cooldown de 30 jours.
