# gup `0.3.0`

> **TL;DR** — `gup` is genuinely cross-platform now. macOS moves from "it compiles" to a first-class target: Homebrew (formulae + casks), Mac App Store and MacPorts are full providers, and a brew-installed binary is finally recognised as such instead of being classified `manual` and hidden from the scan. On Linux, binary ownership resolves through `dpkg -S` / `rpm -qf`. **Breaking: Node ≥ 22.13 required** (previously ≥ 20).

`npm i -g @charles_lindecker/gup@0.3.0`

---

## ⚠️ Breaking

### Node ≥ 22.13.0

`engines` moves from `>=20` to `>=22.13.0`, and the tsup target from `node20` to `node22`.

Node 20 reached EOL on 2026-04-30. Keeping it advertised meant claiming support for a runtime that no longer receives security patches — a hard contradiction to hold for a tool whose whole job is keeping a machine current. The two lines still under support are covered in CI: **22** (Maintenance LTS, until 2027-04) and **24** (Active LTS, until 2028-04).

The build target now tracks `engines`: emitting for an older target silently down-levels syntax the supported runtimes handle natively, and lets code that needs a newer runtime build without complaint.

```bash
node --version   # must be >= 22.13.0
```

## ✨ macOS, for real

### 🍺 Four new OS providers (130 → 134)

| Provider | id | Covers |
|---|---|---|
| Homebrew (formulae) | `brew` | The bulk of the CLI surface on a Mac. **Not gated on darwin**: Linuxbrew (`/home/linuxbrew/.linuxbrew`) goes through the same provider. |
| Homebrew (casks) | `brew-cask` | GUI apps and binary-only distributions dropped into `/Applications` (Docker Desktop, VS Code, JetBrains IDEs, browsers…). |
| Mac App Store | `mas` | The slice of a Mac no other provider can reach: sandboxed installs whose updates sit behind the Store's own auth. |
| MacPorts | `macports` | The other macOS ports tree. Coexists with Homebrew on the same machine and stays invisible to everything else. |

Three deliberate decisions, called out because they change observable behaviour:

- **`brew` and `brew-cask` are separate**, not one provider with two modes. The upgrade command differs (`brew upgrade --formula` vs `--cask`) and casks are the noisy half: `gup list --only brew` now expresses "formulae only".
- **`--greedy` is deliberately omitted** on casks. Without it, brew hides casks marked `auto_updates true` (Chrome, Firefox, VS Code…). Those apps update themselves on launch; forcing a cask upgrade re-downloads a full app bundle to reach a version the app would have fetched anyway.
- **`HOMEBREW_NO_AUTO_UPDATE=1` is not forced.** A scan against a stale index would report "nothing to update" — exactly the failure mode this provider exists to remove. Anyone wanting a strictly offline scan already exports the variable, and we inherit it.

`brew` explicitly refuses to run on win32. That is not cosmetic: people do put a `brew.cmd` shim on the Windows PATH to bridge into WSL (that bridge is the `wsl-brew` provider), and without this guard gup would run `brew outdated` / `brew upgrade` on Windows.

### 🔎 Install-source detection: brew, apt, dnf

This is the fix that unlocks everything else. `InstallSource` gains `brew`, `apt` and `dnf`, and two POSIX refinements sit on top of the plain path match:

**Symlink resolution.** Homebrew installs into a private prefix and only exposes a link on PATH:

```
/opt/homebrew/bin/kubectl → ../Cellar/kubernetes-cli/1.36.3/bin/kubectl
```

`which` reports the link. Without `realpath`, **every brew install classified as `manual` — and `manual` entries are dropped from scan results.** In other words: real upgrades were being silently hidden on macOS. Fixed, and `core/ownership.ts` shares the same resolution so both detectors classify a Homebrew shim by its true Cellar location.

**Package-database probe.** Distro packages land in shared prefixes (`/usr/bin`) that carry no ownership signal in the path itself; `dpkg -S` / `rpm -qf` are the only reliable answer.

Homebrew classification is deliberately conservative: a `Cellar` segment counts **only** under a known prefix (`/opt/homebrew`, `/usr/local`, `/home/linuxbrew/.linuxbrew`, `~/.linuxbrew`). Matching `cellar` alone would route `brew upgrade` at a binary brew does not own if a user happens to have a directory named `cellar` — precisely the misclassification `tests/security/install-source.test.ts` locks down. `/usr/local` is the one prefix that is not brew-exclusive (it is also the classic hand-install location), so it is accepted only in combination with a Cellar/Caskroom segment, never on its own.

The win32 branch is unchanged: no realpath call, no probe.

### 🧩 JetBrains and Eclipse detected on macOS

JetBrains IDEs are now looked for under `/Applications`, `~/Applications` and the Toolbox tree below `Application Support`. A `.app` dropped by `brew install --cask` is followed through to the Caskroom. Bundle scanning is pruned (`Contents/Resources` is not re-explored) so sweeping `/Applications` does not turn into a full recursive walk. Eclipse gets the same treatment.

A sweep across the other IDE providers (Cursor, VSCodium, Windsurf, Zed, Sublime, Obsidian, Notepad++, Unity Hub) so their paths derive from the platform instead of being assumed to be Windows.

### 💬 Platform-aware install hints

`gup doctor` prints a missing provider's `installHint`. A hardcoded `winget install …` is actively unhelpful on a Mac. Providers now declare one hint per platform through `pickInstallHint({ win32, darwin, linux, fallback })`, resolved when the registry is built. `fallback` is mandatory: a hint is never empty, including on a platform nobody enumerated.

Homebrew ids are mapped for the relevant providers along the way (`brew install kubernetes-cli` rather than a generic URL).

## 🐛 Fixes

### `gup --version` no longer lies

The version was declared **twice** in source — `src/cli.ts` and the menu header — and both copies had drifted to `0.1.0` while the package shipped as `0.2.2`. `gup --version` lied, and so did every bug report quoting it.

`src/core/version.ts` now reads `package.json`, with two candidate locations (the module graph is flat after the tsup bundle, nested in development) and a validation by `name` so a stray parent `package.json` can never be picked up. It never throws: a missing `package.json` yields `0.0.0` rather than stopping the CLI from running.

### Double-encoded UTF-8 in the bun and winget parsers

Some sources contained mojibake — UTF-8 read back as latin-1 and re-encoded. Not cosmetic: it was inside the **regexes**.

| File | Broken pattern | Consequence |
|---|---|---|
| `providers/node/bun-global.ts` | `â”œâ”€â”€` instead of `├──` | The `bun pm ls -g` tree never matched → **zero global bun packages detected**. |
| `providers/os/winget.ts` | `mises\s+Ã ` instead of `mises\s+à` | The end-of-table line went unrecognised on a French Windows → winget table parsing skewed. |

### The runner refused Windows 8.3 short paths

`SAFE_COMMAND_PATTERN`, the allowlist filtering the command name before any spawn, did not include `~`. Yet Windows hands back an 8.3 form for any directory whose name exceeds 8 characters or contains a space: `C:\PROGRA~1\nodejs\npm.cmd` and `C:\Users\CHARLE~1\scoop\shims\gh.exe` are ordinary PATH entries, and `%TEMP%` itself is short-form as soon as the username is longer than 8 characters.

On those machines gup refused to spawn a perfectly legitimate binary with `runner: refusing to spawn unsafe command name`. `~` is added to the allowlist and covered by explicit test cases.

The character stays inert as far as injection goes: every callsite that derives a command name from a path runs through execa with shell interpretation off, where argv is passed as a vector; the one shell-routed callsite (scoop) passes a fixed literal, never a derived path.

### `manualChunks` broke the landing build

The Dependabot bump **vite 6.4.2 → 8.0.16** (PR #46) swapped Rollup for **Rolldown**, which only accepts the function form of `manualChunks` — the object map aborted the build with `TypeError: manualChunks is not a function`. The `pages` workflow had therefore been failing on every push touching `index/` since 2026-08-06, and the landing was no longer being redeployed.

Config moved to the function form (understood by both bundlers). `scheduler` deliberately joins the `react` chunk: it is a react-dom runtime dependency, and leaving it out strands it in the entry chunk, which defeats the point of the split.

## 🧪 Tests & CI

### The first test that actually spawns a process

Every other suite mocks `execa` wholesale (`tests/core/runner.test.ts` does `vi.mock("execa")`), which means **the entire suite could be green while the spawn layer was broken**. That blind spot became load-bearing at the execa 9 → 10 upgrade: execa dropped cross-spawn for its own PATH resolver and its own cmd.exe escaper, so *every* command gup runs on Windows is constructed differently — and nothing exercised it.

`tests/integration/runner-spawn.test.ts` adds 15 deliberately unmocked and deliberately cheap tests, so they can run on all six CI legs: argv round-trip with metacharacters, no variable expansion for either shell, empty argument preserved, UTF-8 decoding, non-zero exit without throwing, missing binary, stdout/stderr separation, PATH resolution — plus the Windows cases on `.cmd` shims (npm, pnpm, yarn, corepack, gcloud, az…), which are exactly the code path that changed.

This file is what surfaced the `~` bug above: the GitHub runner has a short-form `%TEMP%` (`C:\Users\RUNNER~1\…`).

### Extended CI matrix

`gup` delegates to a different package manager on every platform and builds OS-specific paths — a single-OS matrix structurally cannot catch a regression on the other two.

| Before | After |
|---|---|
| `windows-latest` × Node 20, 22 | `windows-latest`, `macos-latest`, `ubuntu-latest` × Node **22, 24** |

Windows stays the primary target; macOS and Linux are first-class since the Homebrew/apt/dnf delegation landed.

**Lint gate added.** `CONTRIBUTING` listed lint as part of the PR gate, but no workflow ran it — an eslint bump could introduce violations that nothing surfaced. Restricted to a single leg (`ubuntu-latest` / Node 24): eslint output does not vary by OS or Node line, so running it six times would only slow the matrix down.

**CodeQL alert closed** — `js/regex/missing-regexp-anchor` (high) in `tests/providers/jetbrains-macos.test.ts`. The assertion checked the JetBrains download URL with `toMatch(/jetbrains\.com\/webstorm\/download/)`: unanchored, the pattern also accepts a host that merely embeds that path (`evil.test/jetbrains.com/webstorm/download`). Replaced by a `toContain` on the absolute URL, scheme and host included — stricter than the regex it replaces, and free of regex altogether.

## 🧹 Convention compliance

An audit of the repository against the thresholds declared in `CLAUDE.md` surfaced **78 violations across 167 `src/` files**. All resolved, with no behaviour change — the 2095 tests pass identically before and after.

| Rule | Before | After |
|---|---|---|
| Function ≤ 30 lines | 40 | **0** |
| Cyclomatic complexity ≤ 10 | 22 | **0** |
| Nesting ≤ 3 | 10 | **0** |
| File ≤ 400 lines | 4 | **0** |
| Parameters ≤ 3 | 2 | **0** |

The refactor is almost everywhere the same transformation: `for` loops accumulating an array while filtering on four conditions become a `parseX(line): T | null` function followed by a `.map().filter()`. The parser becomes testable on its own, and the calling method drops to three lines. Applied to `cargo`, `choco`, `scoop`, `mise`, `gcloud`, `gh-extensions`, `arduino-cli`, `winget`.

Two files were split:

- **`providers/ide/jetbrains.ts`** (501 → 356 lines) — the `packageIdsFor` / `productSlug` tables move to `jetbrains-catalog.ts`. That is data tracking the JetBrains catalogue, not provider logic; 120 lines of table were drowning 200 lines of scanning.
- **`commands/menu.ts`** (407 → 347 lines) — the Options screen moves to `menu-options.ts`, the shared state and formatting helpers to `menu-state.ts`.

One latent bug on the way: `runInherit` only exposed the interrupt cause through two local booleans captured in a closure. Grouped into an `InterruptFlags` object owned by `armInterrupts`, the timer and the Ctrl+C handler now share explicit state.

**These limits are a CI gate now**, not a review guideline: `eslint.config.js` enables `max-lines`, `max-lines-per-function`, `max-params`, `max-depth` and `complexity`, and the `Lint` job fails if any is exceeded.

**Dead code is gated too.** CodeQL flagged three unused imports in `commands/menu.ts` — left behind when the Options screen moved out — that neither `tsc --noEmit` nor the lint caught, because nothing was checking. `@typescript-eslint/no-unused-vars` now runs in `eslint.config.js`, and `noUnusedLocals` / `noUnusedParameters` in `tsconfig.json` catch the same class on all six matrix legs rather than the single lint leg.

Both eslint configs also stop reporting unused disable directives. The security ruleset lives in its own config, so every `eslint-disable security/*` in source read as unused from the main lint and every `eslint-disable max-params` read as unused from the security one — nine permanently unactionable warnings that trained readers to skim past lint output. `npm run lint` and `npm run lint:security` now both report zero problems, warnings included.

Comments and blank lines are excluded from the count (`skipComments`, `skipBlankLines`). These ceilings bound what a reader has to hold in their head at once; counting comments would have penalised the repository's comment density and pushed contributors to delete explanations to get green. Two exemptions remain, each justified in place: `max-lines` on `core/registry.ts` (flat catalogue of the 134 providers) and `max-params` on `runPmUpdate` (public signature called from ~40 providers, with `delegateUpdate` as the object-shaped variant).

### esbuild `overrides`

```json
"overrides": { "esbuild": "^0.28.1" }
```

`GHSA-g7r4-m6w7-qqqr` — path traversal in the esbuild *dev server* on Windows: `path.Clean()` is POSIX and does not treat `\` as a separator, so a request for `..\..\..\Windows\system.ini` escapes `servedir`. Fixed in `0.28.1`.

Dependabot could not resolve it: `tsup@8.5.1` (the latest published version) pins `esbuild ^0.27.0`, and the only path npm found downgraded tsup from `8.5.1` to `2.0.3`. The `overrides` entry forces `0.28.1` without touching tsup — build, typecheck and the 2095 tests all pass with it, and the tree dedupes onto a single esbuild copy instead of two.

No effect on consumers of the package: npm only applies `overrides` on the root project, and esbuild is not a runtime dependency of `gup`.

## 🤖 Dependabot reconfigured

`.github/dependabot.yml` moves to a *security-first* posture. The full reasoning lives in the file's comments; in short:

| | Before | After |
|---|---|---|
| Cadence | weekly | **monthly** |
| Settling window | none | **`cooldown`** — 7 d (patch) / 14 d (minor) / 30 d (major) |
| Coverage | `/` npm + `/` actions | **+ `/index`** (the landing only moved on a CVE) |
| Security fixes | scattered | **grouped**, and subject to neither the cooldown nor the PR limit |
| `security` label | applied to everything, no effect | removed (it was a string, not a filter) |

The key point: `cooldown` applies **to version updates only**. An advisory fix lands the day it is published, whatever the schedule says. It is the routine bumps that wait for the ecosystem to have had time to look — most npm compromises (event-stream, ua-parser-js, node-ipc, chalk/debug) were caught and unpublished within hours to a few days.

A single `ignore` is set, on `@types/node` majors, because `ignore` is the one option that also gags security updates — and a types package ships no executable code. Other majors are not ignored, only slowed by the 30-day cooldown.
