# gup `0.3.2`

> **TL;DR** — **19 new providers, 134 → 153.** This release closes the last structural gaps in coverage: the OS package managers that live *beside* the official one (MSYS2, Cygwin, Npackd, Fink, pkgin, Nix, pkgx), the version managers people actually pin their toolchains with (nvm, pyenv, swiftly, mint, vcpkg), and the Windows developer stack that no package manager owns (Visual Studio, Git for Windows, the .NET SDK, NuGet, PSResourceGet). Alongside: the GitHub release lookups are now validated before they leave the process — which fixed a real host-confusion bug — and the landing page is a prerendered site whose numbers are derived from the repository instead of hand-maintained. No flag, no command and no output shape changed.

`npm i -g @charles_lindecker/gup@0.3.2`

---

## 📦 19 new providers

The registry goes from **134 to 153 entries**. These are not long-tail additions: each one covers a class of software that was simply invisible to `gup` before, because nothing else on the machine knows about it either.

### OS package managers beside the official one

| ID | Source |
|---|---|
| `msys2` | MSYS2 pacman set — `pacman -Qu` against **the root's own database** |
| `cygwin` | Cygwin, refreshed through `setup-x86_64.exe` |
| `npackd` | Npackd (`npackdcl` / `ncl`) |
| `fink` | Fink — `fink list --outdated`, upgrades through `sudo` |
| `pkgin` | pkgin (pkgsrc binary packages), upgrades through `sudo` |
| `nix` | Nix binary **and** the user profile (`nix profile upgrade --all`) |
| `pkgx` | the `pkgx` binary itself |

The MSYS2 case is the one that explains the whole group. winget knows there is an *MSYS2 installer* on the machine and nothing whatsoever about the several hundred packages inside its root — so it reports the environment as up to date while everything in it rots. Scanning the root's own pacman database is the only way to see that, and it is exactly the shape of blind spot Cygwin, Fink and pkgin share.

### Version and toolchain managers

| ID | Source |
|---|---|
| `nvm` | nvm (nvm-sh, POSIX) |
| `pyenv` | pyenv (POSIX) |
| `swiftly` | swiftly — Swift toolchain manager (`swiftly self-update`) |
| `mint` | Mint — the global Swift CLI tools it links onto `$PATH` |
| `vcpkg` | vcpkg in classic mode (`vcpkg update`) |

Each of these draws a line between *machine state* and *project state*, and `gup` stays on the machine side. `mint` reports the versions it symlinked into its link directory — the ones actually reachable as commands — and deliberately ignores a project's `Mintfile`, which is repository state: bumping it is a commit, not a maintenance chore. `vcpkg` covers classic mode only, for the same reason: a manifest-mode `vcpkg.json` belongs to the project that ships it.

### The Windows developer stack

| ID | Source |
|---|---|
| `visual-studio` | Visual Studio — `vswhere` plus the release channel manifest |
| `git-for-windows` | Git for Windows, delegating when a package manager owns the binary |
| `dotnet-sdk` | .NET SDK, compared **within its own channel** |
| `nuget` | the NuGet CLI binary (`nuget update -self`) |
| `psresource` | PSGallery through `Get-InstalledPSResource` (PSResourceGet v3) |

`dotnet-sdk` is channel-aware on purpose: an 8.0.x install is not "outdated" because 9.0 exists. Comparing across channels would advertise a major-version migration as a routine update, which is how a build machine ends up on a runtime its projects do not target.

`git-for-windows` illustrates the delegation rule the whole registry follows: when winget, Scoop or Chocolatey owns the binary, the update goes through that package manager rather than around it. Two updaters fighting over the same install is worse than one.

### macOS

| ID | Source |
|---|---|
| `sparkle` | Sparkle appcasts — `SUFeedURL` read from each app bundle |
| `xcodes` | the `xcodes` binary (not the Xcode releases it installs) |

`sparkle` is **scan-only**, and that is the honest shape for it. A very large share of non-App-Store Mac apps ship Sparkle; reading each bundle's `SUFeedURL` and comparing against its appcast is enough to *tell you* what has moved, but the update itself belongs to the app's own updater, which handles code signing and delta patching. Reporting them is useful; driving them from the outside would not be.

`xcodes` follows the same containment rule as the version managers: `gup` updates the manager, never the SDKs it manages. Pulling down a new Xcode is a multi-gigabyte decision the user makes deliberately.

## 🔒 GitHub release lookups are validated before they leave

**65 of the 153 providers** resolve "latest version" through `core/gh-releases.ts`. Until now that helper interpolated its `<owner>/<repo>` argument straight into the API URL. At almost every call site the argument is a literal, so this was inert — but the new `mint` provider derives it from mint's own `metadata.json`, which turned an inert pattern into a live one.

Two things changed:

- **The slug is validated, and the URL is rebuilt from the match.** `<owner>/<repo>` must pass an anchored pattern holding each segment to the characters and lengths GitHub itself allows (39 for an account, 100 for a repository); the request URL is then assembled from the captured groups, not from the input. A slug that fails returns `null` **without a request** — so a hand-edited or half-written metadata file cannot carry a `/`, a `..` or a query string out of `/repos/<owner>/<repo>/` and aim the call at another endpoint.

- **A real host-confusion bug, fixed.** `toGitHubRepo()` matched `github.com` *anywhere* in the git URL. A self-hosted mirror — `https://git.corp/mirrors/github.com/owner/repo.git` — therefore resolved to the slug `owner/repo`, and `gup` would have queried the **public** GitHub repository of the same name and reported its releases as updates for a package that does not come from there. The host match is now anchored, `github.com.evil.test/...` included.

Both fetchers also collapsed onto a shared `fetchReleasesJson()`: they had been carrying two copies of the same fetch-decode-swallow sequence, and adding validation to both would have made it three.

> **A note for whoever reads this file next.** CodeQL reports `js/file-access-to-http` on this helper ("outbound network request depends on file data"), and it is right about the flow — `mint` does derive the slug from a file. That flow *is* the feature, and this query recognises exactly two barriers (`.length` access, generated code), so no amount of validation clears it. What actually leaves the process is one validated slug in a path segment of a hardcoded `api.github.com` URL: no file content, no header, no body, and a host that is never derived from disk — a rule `tests/security/http-targets.test.ts` enforces across all of `src/`. Reviewed and dismissed as a false positive; the reasoning is recorded in the source so it does not get "fixed" twice.

## 🌐 The landing page is now a real site

`index/` was a hand-maintained HTML file. It shipped "~130 providers", "v0.1.0" and "Node >= 20" long after the CLI was at 153, 0.3.1 and Node 22 — across forty-odd occurrences spread through the `<head>`, the JSON-LD graph, the FAQ, `llms.txt`, the manifest and the copy. Numbers a human has to keep in sync drift, and every drifted number is a wrong answer served to a search engine or an AI answer engine.

They are now **derived, once, at build time**:

- `scripts/sync-facts.mjs` regenerates `src/data/facts.js` from the root `package.json` and `src/core/registry.ts` — version, provider count, minimum Node, package name, plus the registered provider ids grouped by domain. It runs as `prebuild` and `predev`, and it **fails the build** if the extracted id list disagrees with `ALL_PROVIDERS`, so the site can never publish a catalogue that contradicts its own count.
- `scripts/stamp-static.mjs` writes those facts into the built `llms.txt`, `llms-full.txt`, `sitemap.xml`, `robots.txt`, `404.html` and `site.webmanifest` — against `dist/`, never the sources, so committed files keep their placeholders and diffs stay deterministic.
- The React tree is **prerendered** into `dist/index.html`, so crawlers and AI fetchers that do not run JavaScript get the real content instead of an empty `#root`.
- `scripts/verify.mjs` gates the result: 48 checks over the built output, the rendered page, the page with JavaScript disabled, `prefers-reduced-motion`, and three viewport widths.

**Build fix in the same area:** Vite 8 no longer depends on esbuild, so `minify: "esbuild"` re-enabled the `vite:esbuild-transpile` plugin and failed the Pages workflow outright on a clean `npm ci`. The site now minifies with **oxc** (Vite 8's default); `target: "es2020"` is unaffected, Rolldown lowers to it natively.

## 🧹 Quality gates

- **Windows CI, real-spawn suites.** `tests/integration/runner-spawn.test.ts` is the only file that spawns unmocked children. Its three bare-name PATH lookups blew past Vitest's 5 s default on `windows-latest` while every absolute-path spawn in the same file finished under 200 ms — Defender inspects each image, the runner's PATH is far longer than a workstation's, and `commandExists` / `whichFirst` walk all of it twice. Those suites now get a 30 s budget; every other suite keeps failing fast on the default.
- **`stamp-static.mjs` no longer checks then reads.** `existsSync()` followed by `readFileSync()` is a check-then-use race, and it reported "missing" for a file that was merely unreadable. One read, one diagnostic.
- Dead imports removed from `sync-facts.mjs`, and an unanchored regex assertion in the NuGet tests replaced by an exact `toContain` on the full download URL.

## ⬆️ Upgrade

```bash
npm i -g @charles_lindecker/gup@0.3.2
gup --version  # 0.3.2
```

Drop-in. No flag, no command, no JSON output shape changed, and no new dependency. The observable difference is that a scan now finds things it used to walk straight past — if that makes a first run longer on a machine carrying several of these toolchains, `gup --fast` skips the providers marked slow (`mint`, `nvm`, `sparkle`, `psresource` among them).
