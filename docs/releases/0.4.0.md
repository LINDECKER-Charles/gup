# gup `0.4.0`

> **TL;DR** — **The terminal no longer freezes on Windows, and the interactive UI is new.** Provider detection used to fire ~140 process creations in one synchronous burst, which on Windows blocks the event loop for seconds — spinner, timers and Ctrl+C all frozen, far longer under an antivirus. Detection now resolves binaries in-process and never blocks; every probe and scan command is also bounded in time and can no longer wait forever on a prompt nobody can see. On top of that, `gup` becomes a **full-screen OpenTUI app** — menu, package table with checkboxes and filter, live scan, dialogs, mouse support — replacing `@inquirer/prompts` and `ora`. **Breaking:** gup now requires **Node ≥ 26.9**.

`npm i -g @charles_lindecker/gup@0.4.0`

---

## 🧊 No more frozen terminal on Windows

The symptom: on some runs the terminal stopped moving — the scan spinner froze, Ctrl+C did nothing — then everything resumed seconds later, or never.

**The cause, measured.** `detectAvailableProviders()` called every provider's `isAvailable()` at once. Most of them check a binary with `where`, so a single scan started **138 `where.exe` processes in one synchronous burst**. On Windows both halves of a spawn run on the main thread — execa's command lookup (a `statSync` per PATH entry × PATHEXT extension) and `CreateProcess` itself — so nothing else could run until the burst was over: **3.3–3.8 s** of fully blocked event loop on a development machine, and much more under Defender, a corporate EDR, or with a network drive on PATH.

**The fix:**

- **`whichFirst` / `commandExists` resolve PATH in-process** with async `lstat`/`stat`, on the libuv threadpool. Same answers as `where` / `which` — same order (bare name, then each PATHEXT extension), same first hit — verified against `where.exe` on 16 binaries and on the full detection set. `lstat` is load-bearing: App Execution Aliases such as `WindowsApps\winget.exe` are reparse points that `stat` rejects with `EACCES`. One deliberate difference: the current directory is no longer searched, so a stray binary in `cwd` does not count as an installed tool.
- **Detection runs 8 probes at a time, each capped at 15 s, and is fail-soft**: a probe that hangs or throws reads as "not installed" instead of holding up, or crashing, the other 150.

| | Before | After |
|---|---|---|
| Synchronous burst at detection | 3.3–3.8 s | **9 ms** |
| Processes spawned by detection | 162 | **13** |
| Worst event-loop stall (warm) | 3.8–5.5 s | ~110–150 ms |
| Full scan, same machine | 11.4 s | **6.5–7.2 s** |
| Providers detected | 27 | 27 — identical set |

**Probes that could wait forever, closed.** Two more ways to hang were found along the way, both indefinite rather than slow:

- `run()` left the child's stdin as an open pipe. A tool that prompts — a source agreement, a credential, a `[Y/n]` — waited for input in a hidden console nobody could type into. stdin is now `ignore`: the prompt reads EOF and fails fast.
- There was no timeout on probes and scans, and execa's timeout only kills the direct child. Every `.cmd`/`.bat` tool runs under `cmd.exe`, so killing `cmd.exe` left the real tool holding the output pipe and execa waiting on it. `run()` now caps every call at 180 s (callers can pass their own) and kills the **whole process tree** (`killDescendants`).

## 🖥️ A full-screen interface, built on OpenTUI

`@inquirer/prompts` and `ora` are gone. `gup` with no subcommand is now a **full-screen OpenTUI app**: a title bar with the session's facts (providers detected, updates available, mode), a menu on the left, the selected view in a bordered panel on the right, dialogs drawn on top, and the keys that apply in a bar at the bottom. Keyboard and mouse both work — click menu entries and rows, scroll lists with the wheel.

| View | What it does |
|---|---|
| **Scan** | Live progress — counter, bar, the providers running — then the result per provider: updates found, failures, and how long each took. `r` rescans. |
| **Paquets** | The outdated packages as a table grouped by provider, current → latest version and the note in columns. |
| **Tout mettre à jour** · **Cible…** | Everything after a confirmation, or `provider:package` targets typed in a dialog that refuses malformed ones on the spot. |
| **Providers** | Detected providers, then the missing ones with their install hint. |
| **Options** | Fast mode, install timeout, and the provider filter as a list to check — no longer a separate prompt. |

**Picking one package or several is now one gesture.** In **Paquets**, `Space` or a click checks a package; on a provider's row it checks the whole provider; `a` checks everything shown; `/` filters by package or provider name, and what is checked *stays* checked while you filter, so narrowing the list to find one more package never loses the others. `Enter` updates what is checked — or, with nothing checked, simply the package (or provider) under the cursor. A confirmation lists what is about to be updated.

**Updates run outside the app, on purpose.** Installers print progress, ask questions and open UAC prompts; they need the real terminal, and a TUI holding the keyboard in raw mode would fight them for it. So once an update is confirmed, gup leaves the full-screen view, the update runs in the normal terminal with its output visible, and `Enter` brings the app back with a fresh scan showing what is left. No OpenTUI renderer is alive while an installer runs.

The one-shot commands get the same building blocks on their own screens: `gup update` without targets opens the **Paquets** table to pick from, `gup list` and `gup update` show the **Scan** view while they scan, and the confirmations and the retry-strategy choice are dialogs. Piped or redirected, none of this is drawn and OpenTUI is never loaded: `gup list --json` and `gup update -y` print exactly what they printed before.

Details behind it:

- **The alternate screen, not a band under the log.** OpenTUI also has a split-footer mode; on teardown, OpenTUI 0.5.14 moved the cursor to a wrong row and cleared everything below it — wiping visible output — whenever the band did not start near the top of the screen (reproduced on Windows). The alternate screen is restored by the terminal itself, with no position to get wrong: when gup exits, the terminal shows exactly what it showed before, plus the install logs.
- **Theme-aware colours.** Everything is painted through the terminal's ANSI palette, like chalk, so light themes stay readable; OpenTUI's named colours are fixed RGB.
- **Panels are plain objects.** Each view holds its state, renders lines for a viewport and takes keys, without touching the terminal — which is how the whole app is tested through OpenTUI's in-memory renderer: keys in, frame text out.
- Ctrl+C still exits at once with code 130.

## ⚠️ Node ≥ 26.9 is now required

OpenTUI's renderer is native code loaded through `node:ffi`. Node enables that module by default from **26.9.0** ([nodejs/node#65475](https://github.com/nodejs/node/pull/65475)); before that it needs `--experimental-ffi`, which an npm bin shim cannot be relied on to pass. The floor moves accordingly: `engines.node >= 26.9.0`, `@types/node` on the 26 line, `tsup` target `node26`, and CI on Node 26 across Windows, macOS and Ubuntu. Node 26 enters Active LTS on 2026-10-28.

Earlier in the same range, the floor had already moved from 22.13 to **24.11**; Node 24 users must now upgrade again.
