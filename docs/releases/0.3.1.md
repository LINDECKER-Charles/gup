# gup `0.3.1`

> **TL;DR** — `gup` now remembers what it did. Every scan and every update attempt is appended to a local JSONL log, one file per calendar month, under the platform's state directory. Nothing reads it back and no UI shows it: the point of this release is to start accumulating the data, so the visualisation that comes later has a history to draw from. Purely additive — no flag, no output format and no command changed.

`npm i -g @charles_lindecker/gup@0.3.1`

---

## 🗂️ Activity history

Until now a run left nothing behind. The terminal scrolled past, and questions as ordinary as *"when did this package last move, and from which version?"* or *"which provider keeps failing on this machine?"* had no answer anywhere. Every invocation started from a blank slate and ended on one.

`gup` now appends what it did to a log:

```
%LOCALAPPDATA%\gup\history\2026-08.jsonl                    # Windows
~/Library/Application Support/gup/history/2026-08.jsonl     # macOS
$XDG_STATE_HOME/gup/history/2026-08.jsonl                   # Linux, default ~/.local/state
```

```jsonc
{"v":1,"ts":"2026-08-08T20:11:04.318Z","runId":"3f2a…","gup":"0.3.1","platform":"win32",
 "kind":"scan","durationMs":8421,"fast":false,"filter":[],"outdated":7,
 "providers":[{"providerId":"winget","outdated":5},{"providerId":"npm-global","outdated":2}]}
{"v":1,"ts":"2026-08-08T20:11:19.902Z","runId":"3f2a…","gup":"0.3.1","platform":"win32",
 "kind":"update","providerId":"npm-global","packageId":"typescript","status":"success",
 "from":"5.9.2","to":"6.0.3","durationMs":14108}
```

### What lands in it

| Record | Carries |
|---|---|
| `scan` | Duration, `fast` mode, provider filter, per-provider outdated count **and scan error**, machine total. |
| `update` | `providerId`, `packageId`, `status` (`success` / `failed` / `skipped`), `from` → `to`, duration, provider message, plus `retry` (which retry strategy was used) and `elevated` (went through the UAC / sudo batch). |

Every record shares the same envelope: `v` (schema version), `ts` (ISO 8601 UTC), `gup`, `platform`, and a `runId` common to every record emitted by the same process. That last field is what makes the log more than a flat list — it stitches a scan back to the updates that followed it, which no amount of timestamp-proximity guessing does reliably once two sessions overlap.

Three distinctions are preserved rather than flattened, because losing them is what makes an activity log useless later:

- **`skipped` is not `failed`.** A provider that deliberately defers (manual download, GUI-managed IDE) and an install the user skipped with Ctrl+C are not errors, and a chart that counts them as such would report a machine as broken.
- **A failed *scan* is not a missing provider.** A provider that was reachable but whose scan threw keeps its record, with the error attached.
- **A retry is tagged as one.** A package that succeeded on the third strategy reads differently from one that succeeded outright.

`gup doctor` writes nothing: it is a read-only probe, not an action.

### Why JSONL

One self-describing object per line, appended, never rewritten.

- **An append is a single `write`.** No read-modify-write cycle, so the elevated child process and its parent can log side by side without a lock — and a process killed mid-write costs one line, not the file. A JSON array would have to be re-serialised in full on every record, and would be corrupt the moment two processes did it at once.
- **No native dependency.** SQLite would have brought one into a package that has none, for a workload that is strictly append-then-read-later.
- **Readable by anything.** `ConvertFrom-Json`, `jq`, pandas, a spreadsheet.

```powershell
Get-Content "$env:LOCALAPPDATA\gup\history\2026-08.jsonl" | ConvertFrom-Json |
  Where-Object kind -eq 'update' | Group-Object status
```

```bash
jq -s 'map(select(.kind=="update" and .status=="success")) | length' ~/.local/state/gup/history/*.jsonl
```

Monthly shards, not one growing file and not one per day: a month stays small enough to parse in a single read, and a year of activity is twelve files instead of three hundred and sixty-five. No rotation logic to get wrong.

### Three guarantees

- **It never breaks an update.** A full disk, a read-only profile or a locked file costs one dimmed warning — on **stderr**, never stdout, because `gup list --json` is a pipe — and the upgrade proceeds. The warning is emitted once per process, so a long batch cannot turn into a wall of the same line.
- **Writes are synchronous.** Every command in `cli.ts` ends on `process.exit(code)`, which does not drain pending async I/O. A fire-and-forget append would routinely lose the last records of a run — precisely the ones describing what just happened. At these sizes the syscall is noise next to spawning an installer.
- **It is write-only inside the tool.** Nothing reads the log back, so a truncated, tampered or hand-edited file can never change how an update behaves. The stateless-orchestrator property of `gup` is intact: no run's behaviour depends on a previous one.

### Opting out

| Variable | Effect |
|---|---|
| `GUP_HISTORY=0` | Disables the history entirely (`false`, `off`, `no` also accepted) |
| `GUP_HISTORY_DIR=<path>` | Writes the shards elsewhere |

When the platform exposes no usable anchor (no `%LOCALAPPDATA%`, no home directory), the history turns itself off rather than inventing a path — writing a log into whatever directory the user happens to be in would be worse than not writing one.

## 🧹 The seam that made it possible

Four call sites used to invoke `provider.update()` directly, each pairing it with its own `finalizeOutcome()` call: the two batch loops (`commands/update.ts`, `commands/menu.ts`), the targeted path, and the retry pass in `ui/retry-failed.ts`. Anything that must happen around *every* update had nowhere to live but those four copies — which is exactly how one of them ends up forgotten.

They now share **`ui/apply-update.ts`**, which dispatches, normalises the outcome through the skip controller, and records, in one place. Two consequences beyond the history itself:

- The duplicated `updateEach` loops in `commands/update.ts` and `commands/menu.ts` — same body, same comment, two files — collapse into a single `applyEach`.
- Per-package durations come for free, since the seam owns the timing.

The elevated batch stays the deliberate exception. The child process remains a pure executor and never touches the history; its parent logs the outcomes that come back, tagged `elevated`. That keeps every record in the *invoking* user's profile — not necessarily the account UAC elevated into — and rules out logging the same attempt twice. The cost is per-attempt durations on that path, which are left absent rather than faked from the batch total.

## 🧪 Tests

**28 new tests across 3 files**, and one line of test-harness policy:

| File | Covers |
|---|---|
| `tests/core/history-paths.test.ts` | Data-root resolution on win32 / darwin / linux, `$XDG_STATE_HOME` and `$HOME` fallbacks, the `GUP_HISTORY_DIR` override, UTC month shard naming, and the two cases that must resolve to `null`. |
| `tests/core/history-store.test.ts` | Envelope contents, shared `runId` across a run, `success` / `failed` / `skipped` mapping, version delta and flags, omission of unset optional fields, scan aggregation, all four opt-out spellings, and an unwritable location warning once without throwing. |
| `tests/ui/apply-update.test.ts` | Dispatch shape, that the *finalized* outcome is what gets returned and logged, option/retry forwarding, and that `applyEach` stops before the next package once the batch is aborted. |

`vitest.config.ts` now sets `GUP_HISTORY: "0"` for the whole suite: the writer is reached transitively by the command and UI suites, and a test run has no business appending to the developer's real profile. The two suites that exercise it re-enable it against a `mkdtemp` directory.

Both are qualified rather than dropped: `gup` remains stateless in the sense that matters, since what it now writes is never read back. `core/history/` documented in §9 with the decisions above; `ui/apply-update.ts` and `ui/skip-controller.ts` added to the tree layout.
- `SECURITY.md` — the log is plain text under the user's own state directory: package ids, versions, outcomes. No credential, no path outside it, no network egress, and never read back, so a tampered log cannot influence an upgrade.

```bash
npm i -g @charles_lindecker/gup@0.3.1
```

Drop-in. No flag, no command, no JSON output shape changed, and no new dependency. The only observable difference is a file that starts existing after the first run — `GUP_HISTORY=0` if you would rather it did not.
