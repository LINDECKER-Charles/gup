# gup `0.6.0`

> **TL;DR** — **Tell the maintainer what went wrong, and let them see it.** `gup feedback` and the app's new **Feedback** view open a bug/idea form prefilled with your install ID; a one-time question — **No** by default — offers to share your activity history and debug log, redacted, about once a week, so a report comes with the journals behind it. On the update side: Homebrew no longer stops on its own `[y/n]`, a failed install says why in its installer's words, a Homebrew formula blocked by its build tools and a winget package that refuses an elevated installer end as skips that name the fix, five tools are no longer updated twice in one run, and `pip` sees the packages of a Python you own. Dev-only advisories are closed.

`npm i -g @charles_lindecker/gup@0.6.0 --allow-scripts=node-pty`

## 💬 Feedback and journal sharing

```bash
gup feedback               # print the install ID and the form's address, open the form
gup feedback id            # the install ID alone
gup feedback share on|off  # off also erases what was shared
gup feedback status        # sharing, install ID, last upload, next sync
```

- **A form that already knows the context.** The form lives on the [landing site](https://lindecker-charles.github.io/gup/#feedback), in eight languages, with or without JavaScript. Opened from gup, it is filled with the install ID, gup's version and the platform. You can report a bug without sharing anything.
- **Sharing is asked once, and No is the answer by default.** The first time you open the app, or run `gup update` or `gup list` in a terminal, gup asks whether to share its journals. Escape and Ctrl+C answer no. Scheduled runs, CI, `--json`, `--yes` and `GUP_SHARE_LOGS=0` are never asked. The answer stays on this machine: a yes given on one machine never starts uploads from another.
- **What is sent.** The [activity history](https://github.com/LINDECKER-Charles/gup/blob/main/docs/guide/journal-and-reports.md) and the debug log, redacted exactly as `gup log export` redacts them: secrets removed, your home folder shown as `~`, no environment variables, no OS release. The settings file is never read for it.
- **When.** About once a week, after the app closes, after `update`, `list` or a scheduled run, and at once when you open the feedback form. The first sync sends the whole local history; a sync cut short carries on at the next run. An upload takes a few seconds at most, never prints anything and never fails a command.
- **An identity nobody can borrow.** The install ID derives from an Ed25519 key pair gup creates on first need, kept in the machine-local state directory. The private key signs every upload and erasure and never leaves the machine. Looking at where things stand (`gup feedback status`, `gup doctor`) never creates it.
- **Changing your mind.** `gup feedback share off`, or Options › **Share journals**, stops sharing and asks the service to erase everything this install sent. The service keeps shared journals for 90 days.

The [feedback guide](https://github.com/LINDECKER-Charles/gup/blob/main/docs/guide/feedback-and-sharing.md) has the details.

### The service behind it

Reports and journals land in a new service, [`feedback/`](https://github.com/LINDECKER-Charles/gup/tree/main/feedback) in the repository, deployed at `https://feedback.global-updater.com`. It is not part of the npm package. It is built on Fastify and PostgreSQL and relays every new report by mail. Its back office is server-rendered with no client script and a strict CSP. It sits behind a password and an authenticator-app code. From it, the maintainer triages reports and reads each install's journals run by run. An MCP endpoint gives an assistant access too, through accesses that each carry permissions and an expiry. The contract between the CLI, the landing and the service is in [`feedback-service.md`](https://github.com/LINDECKER-Charles/gup/blob/main/docs/development/feedback-service.md).

## 🍺 Homebrew never waits on itself

Since Homebrew 6.0, ask mode is the default. An upgrade that also moves another package asks `Do you want to proceed with the upgrade? [y/n]` whenever it has a terminal, and gup's embedded terminal is one. Such an upgrade pulls in a dependent or a new dependency, the way `dotnet` pulls `powershell`. So a package you had already checked waited for a `y`. Every `brew upgrade` gup runs now sets `HOMEBREW_NO_ASK=1`: `brew`, `brew-cask`, tools delegated to Homebrew, and `wsl-brew`. The variable is used rather than `--yes`, which a Homebrew older than 6.0 refuses.

A formula with no bottle for your Mac builds from source, and Homebrew checks the build tools first. When they block it, the formula now ends as a **manual action that names the fix**, no longer as a failure offered again at every run. Four blocks are covered:

- Command Line Tools that do not support this macOS, or are too old;
- Xcode too old;
- no developer tools;
- the Xcode license not accepted.

## 🧾 A failed install says why

Most providers report a failure without a reason. The run view, the journal, the HTML report and the history were then left with a bare "failed". When the output was kept, the outcome now takes the line that says why: the first line that opens on `Error:`, `error:`, `fatal:`, `npm error` or apt's `E:`, else the last one. The output is kept by the app's terminal pane and by scheduled runs. The debug log's line for a failed command shows that same line, rather than the advice Homebrew prints last.

## 🪟 winget's elevation refusal is a skip

Some manifests forbid an elevated installer. When gup runs elevated, winget answers `0x8A150056` (`INSTALLER_PROHIBITS_ELEVATION`), and Spotify failed this way at every run. Every retry tier runs in the same elevated context. The reinstall tier even uninstalled the application before an install winget then refused. The package now ends as a skip that says to run `winget upgrade --id <id>` from a terminal that is not elevated.

## 🔁 Nothing updated twice

Five tools had two rows in the same scan, and the second update failed or did nothing:

| Tool | First row | Second row, and what it did | Now updated by |
|---|---|---|---|
| Git for Windows | `git-for-windows` provider, which left its installer running | winget's `Git.Git` met that installer | `git-for-windows` |
| semgrep | `uv-tools` (a semgrep installed as a uv tool) | the `semgrep` provider skipped with "host Python not found" | `uv-tools` (or `pipx`) |
| pnpm | `pnpm-g` | `self`'s `pnpm` failed with "still on PATH" | `self`, which checks that the `pnpm` on `PATH` changed |
| npm | `npm-g` | `self`'s `npm` repeated the upgrade | `npm-g` |
| pip | `pip` | `self`'s `pip` repeated the upgrade | `pip` |

The [troubleshooting guide](https://github.com/LINDECKER-Charles/gup/blob/main/docs/guide/troubleshooting.md) lists the pairs.

## 🐍 pip sees the Python you own

`pip` listed the user site only. Behind the `pip` on `PATH` there may be a Python whose site-packages are yours to write: a python.org install "for me only", a Python in one of your folders, pyenv. On one machine that hid 73 of 75 outdated packages. It also kept a pin held there, `opentelemetry-proto` capping `protobuf` below 7, from ever being lifted. gup now also covers that folder. Each package is upgraded in the site it lives in, and put back there after a breaking upgrade. In that folder gup runs without `--user`, which would only have added a shadowing copy.

The folder is left alone when:

- it is externally managed (PEP 668: Homebrew, Debian);
- it belongs to a virtual or conda environment;
- it is not writable.

## ⬆️ Upgrade

```bash
npm i -g @charles_lindecker/gup@0.6.0 --allow-scripts=node-pty
gup --version     # 0.6.0
gup feedback      # the form, with your install ID
```

**Drop-in** on Node 26.9 or newer: same commands, flags, settings file, schedules and history. One thing is new: the sharing question, asked once in a terminal before the app, `update` or `list`. Answer it, or press Escape, and the command goes on; until you say yes, nothing leaves the machine.
