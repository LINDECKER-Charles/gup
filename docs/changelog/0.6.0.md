# 0.6.0 — 2026-11-22

[Release notes](../releases/0.6.0.md) · [GitHub Release](https://github.com/LINDECKER-Charles/gup/releases/tag/0.6.0) · [npm](https://www.npmjs.com/package/@charles_lindecker/gup/v/0.6.0) · [Compare `0.5.3...0.6.0`](https://github.com/LINDECKER-Charles/gup/compare/0.5.3...0.6.0)

**85 commits** · Charles Lindecker, dependabot[bot]

0.6.0 lets a user report a bug or an idea and, when they agree, share their journals with the maintainer. `gup feedback` and the app's new Feedback view open a form on the landing site, prefilled with an install ID that gup derives from a key pair it keeps on the machine; a one-time question, answered no by default, asks whether to send the activity history and the debug log — redacted as `gup log export` redacts them — about once a week. Both land in the new feedback service (`feedback/`, deployed to `https://feedback.global-updater.com`, not part of the npm package): a French back office behind a password and a TOTP code, a mail relay, and an MCP endpoint whose accesses carry permissions and an expiry. On the update side, Homebrew no longer waits on its own confirmation, a Homebrew formula blocked by its build tools and a winget package that refuses an elevated installer end as skips that name the fix, a failed install says why in its installer's own words, Git for Windows, semgrep, npm, pip and pnpm are no longer updated twice in one run, and `pip` covers the site-packages of a Python the user owns. Advisories in vite, vitest, happy-dom, minimatch (through eslint), source-map-js and lighthouse's transitives are closed. Eleven pull requests reached `main`, [#103](https://github.com/LINDECKER-Charles/gup/pull/103) to [#131](https://github.com/LINDECKER-Charles/gup/pull/131); the Dependabot PRs [#105](https://github.com/LINDECKER-Charles/gup/pull/105) to [#107](https://github.com/LINDECKER-Charles/gup/pull/107) went through their batch branches, and the release through [#132](https://github.com/LINDECKER-Charles/gup/pull/132).

## Added

- **core/feedback:** each install owns an Ed25519 key pair, created on first explicit need and kept in the machine-local state directory; its public install ID (UUID shape) derives from the public key, so nobody else can claim it. When the user agreed, the history and the debug log are redacted the way `gup log export` does (environment and OS release dropped as well) and uploaded in signed batches of at most 1000 items after a menu session, an update, a list or a scheduled run, within a 5 s budget; nothing is sent while the question is unanswered or `GUP_SHARE_LOGS` is off ([`2d7d4c1`](https://github.com/LINDECKER-Charles/gup/commit/2d7d4c1), [#131](https://github.com/LINDECKER-Charles/gup/pull/131))
- **core/feedback:** the journals are synced about once a week instead of after every command; a sync cut short carries on at the next command, opening the feedback form syncs at once, the first sync sends the whole local history, and `gup feedback status` shows when the next one is due ([`305738b`](https://github.com/LINDECKER-Charles/gup/commit/305738b), [#131](https://github.com/LINDECKER-Charles/gup/pull/131))
- **ui:** a Feedback view in the menu (install ID, form link, copy), a "Share journals" row in Options, and the one-time consent question, default no ([`31967f5`](https://github.com/LINDECKER-Charles/gup/commit/31967f5), [#131](https://github.com/LINDECKER-Charles/gup/pull/131))

The question is asked once before the menu, `update` or `list`, never in unattended runs. Links and uploads target `https://feedback.global-updater.com` ([`98d27ac`](https://github.com/LINDECKER-Charles/gup/commit/98d27ac), [`eb3464c`](https://github.com/LINDECKER-Charles/gup/commit/eb3464c), [#131](https://github.com/LINDECKER-Charles/gup/pull/131))

## Fixed

- **providers:** a Homebrew upgrade no longer stops on "Do you want to proceed with the upgrade? [y/n]". Since Homebrew 6.0, ask mode is the default: an upgrade that also moves another package (a dependent, a new dependency, `dotnet` pulling `powershell`) asks first whenever it has a terminal, and the embedded terminal is one, so a package already checked in gup waited for a `y`. Every `brew upgrade` gup runs — `brew`, `brew-cask`, a tool delegated to Homebrew and `wsl-brew` — now sets `HOMEBREW_NO_ASK=1`; the variable rather than `--yes`, which a Homebrew older than 6.0 refuses ([`3ee09ab`](https://github.com/LINDECKER-Charles/gup/commit/3ee09ab), [#109](https://github.com/LINDECKER-Charles/gup/pull/109))
- **core:** a failed update no longer ends as a bare "failed" when its provider gives no reason — most of them answer a failure without one, which left the run view, the journal, the HTML report and the history with nothing to show. When an install sink kept the output (the app's terminal pane, a scheduled run), the outcome takes the line that says why: the first that opens on `Error:`, `error:`, `fatal:`, `npm error` or apt's `E:`, else the last. A scheduled run keeps the last 2 KB of a failed install's output for it, past the log's byte budget ([`47f8588`](https://github.com/LINDECKER-Charles/gup/commit/47f8588), [#110](https://github.com/LINDECKER-Charles/gup/pull/110))
- **ui:** a failed command's line in the debug log (`gup log`, the Journal's Debug tab) shows that same line rather than the last one, which Homebrew spends on advice ([`66d9b26`](https://github.com/LINDECKER-Charles/gup/commit/66d9b26), [#110](https://github.com/LINDECKER-Charles/gup/pull/110))
- **providers/os:** a Homebrew formula stopped by its build tools ends as a manual action that names the fix, no longer as a failure offered again at every run. A formula with no bottle for this Mac installs from source, and Homebrew checks the build tools first: Command Line Tools that do not support this macOS (`Your Command Line Tools (CLT) does not support macOS 27.`) or are too old, Xcode too old, no developer tools, the Xcode license not accepted. `symfony-cli/tap/symfony-cli`, a tap formula without bottles, failed this way at every run on macOS 27 while the bottled formulae of the same batch went through ([`d122cf1`](https://github.com/LINDECKER-Charles/gup/commit/d122cf1), [#110](https://github.com/LINDECKER-Charles/gup/pull/110))
- **providers/os:** a winget package whose installer refuses to run as administrator ends as a skip that says what to run, no longer as a failure offered for retry. winget answers `0x8A150056` (`INSTALLER_PROHIBITS_ELEVATION`) when the manifest forbids an elevated installer and its own process is elevated: Spotify failed this way at every run since October. Every retry tier runs in the same context, and the reinstall tier uninstalls the application before an install winget then refuses. The skip says to run `winget upgrade --id <id>` from a terminal that is not elevated ([`0601ff6`](https://github.com/LINDECKER-Charles/gup/commit/0601ff6), [#129](https://github.com/LINDECKER-Charles/gup/pull/129))
- **core:** Git for Windows, semgrep, npm, pip and pnpm are no longer updated twice in one run. Each had two rows in the same scan, and the second update failed or did nothing: winget's `Git.Git` met the installer the `git-for-windows` provider had left running in the background; the `semgrep` provider skipped with "host Python not found" for a semgrep installed as a uv tool, which the `uv-tools` row updated; `self`'s `pnpm`, run after `pnpm-g`'s, found the version `pnpm-g` had just installed and failed with "still on PATH"; `self`'s `npm` and `pip` repeated `npm-g`'s and `pip`'s upgrade. When both providers list the software, `Git.Git` now gives way to `git-for-windows`, `semgrep` to `uv-tools` or `pipx`, `self`'s `npm` and `pip` to `npm-g` and `pip`, and `pnpm-g`'s `pnpm` to `self`'s, which checks that the `pnpm` on `PATH` changed ([`a88a6d1`](https://github.com/LINDECKER-Charles/gup/commit/a88a6d1), [#129](https://github.com/LINDECKER-Charles/gup/pull/129))
- **providers/python:** `pip` also lists and upgrades the site-packages of the Python behind the `pip` on `PATH` when that folder is the user's to write — a python.org install "for me only", a Python in a folder of the user's, pyenv — instead of the user site alone, which hid 73 of 75 outdated packages on one machine and kept a pin held there (`opentelemetry-proto` capping `protobuf` below 7) from ever being lifted. Each package is upgraded, and put back after a breaking upgrade, in the site it lives in: without `--user` there, which would only have added a shadowing copy. The folder is left alone when it is externally managed (PEP 668: Homebrew, Debian), belongs to a virtual or conda environment, or is not writable ([`74150e4`](https://github.com/LINDECKER-Charles/gup/commit/74150e4), [#104](https://github.com/LINDECKER-Charles/gup/pull/104))
